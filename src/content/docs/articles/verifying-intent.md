给一个应用加深色模式，做到什么程度才算完成？

按钮能切换颜色，算不算？刷新页面后偏好还在吗？用键盘能不能操作？浏览器不允许保存本地数据时怎么办？这些问题如果留到合并代码时才问，评审者就得一边读实现，一边补需求。

Ankit Jain 在 Tessl 的[《We stopped reviewing code and started verifying intent》](https://tessl.io/blog/we-stopped-reviewing-code-and-started-verifying-intent)里，提出把这场讨论搬到写代码之前。我认同这个调整。不过，读完之后，我更在意随之而来的责任：当人开始依据验收报告放行，谁来检查报告没有问错问题？

![意图验证：任务验收、团队不变量、实际结果与规则责任](https://cdn.jsdelivr.net/gh/NTLx/Pic@master/wechat-articles/2026-11-07-verifying-intent-00-infographic-core-summary.png)

## 让评审者先知道要找什么

Jain 描述的变化很具体：生成代码之前，先由人审查意图、验收条件、约束和边界情况。实现完成后，再围绕这些条件给出验证结果和证据。

原文的深色模式截图很适合解释这种做法。它把首次访问的默认主题、切换操作、偏好保存、深色样式覆盖、浅色模式回归分别写成验收项，其中还明确要求键盘可操作、控件有无障碍标签。评审者因此知道要检查哪些行为，不必从改动的文件里猜作者想解决什么。

下图来自原文。值得看的是验收条件旁边的证据入口，以及任务条件与团队规则的分区；绿色状态本身并不能说明验证覆盖充分。

![原文截图：深色模式验收条件、证据入口与团队不变量](https://cdn.jsdelivr.net/gh/NTLx/Pic@master/wechat-articles/2026-11-07-verifying-intent-01-source-intent.png)

我觉得这种前移的价值在于，把原本藏在评审者脑子里的预期变成了可以争论的对象。例如“跟随系统主题”看起来很自然，但截图的要求却是首次访问默认浅色。这属于产品选择，不能靠代码写得漂亮来决定。

先谈清楚这些选择，后面的测试才知道应该坚持什么。否则，实现和测试即使彼此吻合，也可能一起误解需求。

## 把重复评论变成有人维护的规则

任务验收回答的是：这次应该改变什么？团队不变量回答的是：无论这次改什么，哪些约束都应该成立？

原文列举了货币使用 Money 类型、禁止直接写 users 表、只使用结构化日志等例子。相比“请写得更规范”，这些规则指向具体对象，也比较容易追问违反后会发生什么。

原文另一张截图展示了规则库。规则带着分类、来源和团队归属，其中有来自 PR 评论的条目。这一点比规则数量更值得注意：评论被保留下来之后，应该能找到它适用的范围，以及负责解释它的人。

![原文截图：按分类、评论来源和团队归属组织的不变量库](https://cdn.jsdelivr.net/gh/NTLx/Pic@master/wechat-articles/2026-11-07-verifying-intent-02-source-invariants.png)

我赞成从重复评论里找规则，但不赞成直接把高频评论升级成硬门槛。“这个地方最好拆一个函数”可能依赖上下文；“缓存键必须区分租户”则涉及隔离约束。频率能提示哪里反复消耗注意力，不能代替对风险和适用范围的判断。

规则也需要被质疑。技术栈变了，旧约束可能不再合适；临时豁免多了，可能说明检查器太粗，也可能说明团队正在绕过一个仍然必要的限制。让评论自动执行之后，仍然需要维护规则。

## 判定可以重复，标准仍然可能漏项

读到原文用“确定性结论”描述验收时，我会把这件事拆开看。

我查了 Aviator 的[验证机制文档](https://docs.aviator.co/verify/concepts/how-verification-works)，发现它对这一点有更细的限定：代码扫描的结论可确定性复现；运行时验证由使用 LLM 的 Agent 操作预览环境，不能严格保证每次重跑一致。文档提到用缓存避免相同内容重复执行，但复用已有结果与重新执行后得到相同结果，是不同的事。

即使先放下这种运行差异，标准本身仍会遗漏。类型检查、精确断言可以给出明确的通过或失败；“页面是否易用”“所有重要场景是否覆盖”却需要额外判断。哪怕某条命令每次都稳定返回通过，也只能说明它检查的条件成立，不能证明条件已经完整表达了目标。

假设团队要给多租户应用增加缓存。验收写了读取成功、缓存命中、过期后刷新，测试也都通过。但如果没有问过不同租户能否读到彼此的数据，这份报告就可能放行一个严重缺陷。这里缺少的是隔离条件，继续重复已有测试没有帮助。

这是假设场景，并非原文报告的事故。它让我看到意图验证的代价：需求里没有表达的东西，更容易从验收报告中消失。人工评审仍有必要主动寻找反例，尤其要问：有没有某种实现，能满足这张清单，却违背业务目的？

站内此前的[《测试通过之后，Agent 还欠你一条证据链》](https://ntlx.github.io/articles/agent-evaluation-evidence-chain)讨论过如何保留基线、运行轨迹和可复现的失败。沿着这个问题往前，我想再补上验收标准的来历：证据能解释一次检查发生了什么，业务判断还要解释为什么检查这些东西。

## 写实现的人，能否顺手改掉裁判

Jain 在原文链接的前篇[《How to Kill the Code Review》](https://latent.space/p/reviews-dead/)里，已经提醒过：验证标准应来自规格，而不是从实现中推导。这里的约束很明确：先决定要验证什么，再实现。

我还想把这个要求落到修改权限上。假如负责实现的 Agent 可以同时弱化验收标准、删掉失败测试，再提交一份全绿报告，那么标准事先存在也不足以建立信任。

比较可行的做法，是把修改规则本身视为需要解释的变更。实现可以迭代；如果必须调整验收条件，就把调整原因交还给负责需求或风险的人。验证者可以指出标准不合理，但不能默默把它改成容易通过的版本。

原文最后提出“Own”：需要有人负责验证规则。责任不能只停在配置文件的作者名字上，还要包括谁处理误报、谁批准豁免，以及发生漏检后谁决定补什么。

我不会因此宣布逐行阅读已经过时。权限边界、数据迁移、并发状态等敏感改动，可能仍值得检查具体实现。意图验证为减少例行阅读提供了依据，却没有替每个团队回答哪些代码可以放心略过。

## 先试一次能不能拒绝错误

如果把这篇文章的启发带回日常开发，我会先挑一种边界清楚、能够回滚的改动试行。

动手前写出预期行为、禁止破坏的条件，以及验证方式。交付时把实际结果和对应证据放在一起，让接手的人能重跑。然后，故意制造一种违反约定的实现，观察验证器能否拒绝它。

比如已有“缓存按租户隔离”的约束，就试着让缓存键遗漏租户信息。如果检查仍然通过，应先修验证方式，再考虑减少人工检查。这个小实验比“我们增加了一条规则”更能说明规则有没有起作用。

试行时也应保留抽查：从已通过的改动中找遗漏，把新发现带回下一次验收。抽查的作用是修正标准的盲区，而非机械地再看一遍报告。

我读这篇文章最大的收获，是愿意把更多评审时间花在开工之前：讨论哪些行为必须成立，哪些风险值得怀疑，失败时要留下什么。等到证据足够可靠，再逐步减少重复劳动。团队需要亲自确认这种可靠性，不能用一份绿色清单代替这个判断。
